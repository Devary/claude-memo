# CrudStone — metadata-driven CRUD generator (explored 2026-07-19)

Two repos in `/home/devary/sandbox/gen/`, together forming a **context-driven CRUD generator**: an entity is described once as a "context" (fields, widget types, allowed actions) and the UI renders a full CRUD screen from it — no per-entity code.

## context-gen (LIBRARY, Quarkus 3.30.3, Java 17)
**Confirmed by user 2026-07-20: context-gen is a LIBRARY, not a standalone service.** It gets imported as a Maven dependency into any backend project to provide the UI-context capability: the host app ships its own YAML context files and serves them to dynamic-crud (hence prod contextUrl → `pollanime-core-jvm:5555/context/` — the host serves contexts). The Quarkus app shell / port 9444 / TestResource are only a dev harness.
- Branch `main`, package `org.devary.table`. Very early skeleton (~7 tiny classes).
- `TableContext` (name, path, allowActions, allowedActions, allowExportAction, disabledActions, disabledFields, Set<Field>) + `Field` (name, type, ListType, customCallParams, fieldObjectsFilter, createEditStrategy).
- `ContextLoader` parses YAML via jackson-dataformat-yaml into `TableContext`.
- One sample context: `src/main/resources/context/sharacter.yaml`.
- CORS wide open, GET only. GitHub Actions Maven workflow exists.
- **Empty placeholders**: `FieldType` + `ListType` enums empty, `CustomCallParams` + `ObjectFilter` classes empty, `CreateEditStrategy` = single String `fieldType`.
- **BUG**: `TestResource` GET `/sharacter` reads `getResourceAsStream("sharacter.txt")` — wrong name AND wrong relative path (resource is `/context/sharacter.yaml`) → NPE at runtime. No generic `GET /context/{name}` endpoint exists yet, though the frontend expects exactly that (`environment.contextUrl + name`).

## dynamic-crud (frontend, `@devary/crudstone` 1.0.6, Angular 19 + PrimeNG 19 Aura + Tailwind, dev port 5900)
- Branch `master`, repo url github.com/devary/crudstone, publishConfig → GitHub Packages (intended as a library).
- **Core**: `DynamicTableComponent` (`d-dt` selector, ~290 lines) renders the whole CRUD from an `EntityContext` input: PrimeNG table with per-column filters, pagination, multi-row select, CSV export, create/edit dialog (widget chosen by `createEditStrategy.fieldType`), delete with ConfirmDialog, toasts via `MessageTemplateService` (entity+action tuple).
- `EntityContext`/`TableField` mirror the backend model; `TableFieldType` = inputText | textEditor | multiSelect | simpleSelect.
- `ContextService`: loads `EntityContext` JSON from `environment.contextUrl + name`, caches in a Map, emits on `ctx$` BehaviorSubject. `AbstractService`: generic CRUD (getAll/getOne/create/update/delete) — **ignores context `path`**, builds uri as `apiUrl + context.name` (local mode appends `.json` to read `assets/data/*.json`).
- Demo entities: anime + sharacter ("sharacter" spelling is deliberate branding). Contexts in `assets/data/contexts/context.{anime,sharacter}.json`; sample data `anime.json`/`sharacter.json`. Per-entity wrapper components (AnimeComponent, SharacterComponent) just call `loadContext(name)` — pure duplication, should be one dynamic `/:entity` route.
- Placeholder components scaffolded but empty: stepper, text-editor, object-list (object-list used for multiSelect "show more" dialog).
- Docker: nginx:alpine serving `dist/dynamic-crud/browser` on 5900, `/api/` proxied to `pollanime-core-jvm:5555` → the project grew out of the anime-poll ecosystem.

## Two more bugs found+fixed (2026-07-22, user-reported) — 11 backend + 11 Cypress tests green, ng build clean
1. **Multiselect/select overlay panel clipped by the entity dialog**: `p-select`/`p-multiselect` in entity-form-dialog were rendered WITHOUT `appendTo="body"`, so PrimeNG nested the option panel inside `.p-dialog-content`'s DOM subtree — even with a higher computed z-index (2104 vs dialog's 1102), the panel got visually clipped by the dialog's own box. Fixed by adding `appendTo="body"` to both. Verified by dumping the DOM ancestor chain in a throwaway Cypress spec (panel was nested 6 levels inside `.p-dialog-content` before the fix).
2. **"Show more" dialog (multiSelect tag overflow) was BOTH mistitled AND rendered empty**:
   - Mistitle: `showMore()` built the header as `` `List of ${this.context().name}s` `` — `context()` is always the TABLE's own context (e.g. "animes"), never the related entity, and the trailing `s` on an already-plural name produced "List of animess". Fixed: `showMore` now takes the `field` too and titles with `field.listType ?? field.name` (the actual related entity name, e.g. "sharacters") — no manual pluralization.
   - Empty content: a REAL ANGULAR COMPILER BUG. `object-list.component.html` had `@for (obj of data; track obj.id ?? obj.name)` — the `??` inside a `track` expression produced Ivy-generated code referencing an undefined temporary (`tmp_1_0 is not defined`), so the loop silently rendered zero views even though `data` was correctly populated (confirmed via `ng.getComponent(el).data` showing the right array while `el.innerHTML` was just `<!--container-->`). Fixed by simplifying to `track obj.id` (ids are always present — generic EntityStore always assigns a UUID). **Lesson: never use `??`/ternary/complex expressions inside `@for`'s `track`; track by a single guaranteed-present property.**
   - New permanent regression tests in entity-table.cy.ts: dialog title + content assertions, and overlay-not-clipped assertion.
   - Debugging technique used: `win.ng.getComponent(el)` / `win.ng.applyChanges(...)` (Angular's built-in devtools globals, exposed automatically in dev builds) to inspect a live component instance's actual field values vs. its rendered DOM — this is how the track-expression bug was isolated from a data-plumbing bug.

## Empty-value column filter + live text filtering (2026-07-22, by Claude — 14 Cypress tests green x2, ng build clean)
- **"(Empty)" filter option**: `DynamicTableComponent` has a private `emptyOption = {id: '__empty__', name: '(Empty)'}` sentinel. `filterOptionsFor(field)` prepends it to `selectOptions()[field.name]` for the column-filter template (NOT the create/edit dialog's own select — scope is filter-only). The `inRelatedList` FilterService predicate checks `isRowEmpty` (empty array or falsy) first: if the sentinel is among the selected filter options AND the row is empty, it matches; the sentinel id is stripped before matching real ids so it never collides with a real UUID.
- **Live text filtering**: root cause found by reading PrimeNG's own source (`primeng-table.mjs`, `ColumnFilterFormElement.onModelChange`) — for `type="text"`, PrimeNG only calls `_filter()` immediately when the value becomes `''`; otherwise filtering waits for Enter or the Apply button in the overlay menu. `[showMenu]="false"` alone does NOT change this (it's independent gating logic). Fix: replaced the plain `<p-columnFilter type="text">` with a custom `pTemplate="filter"` template (same pattern as the select/multiSelect filters) — a plain `pInputText` bound `(ngModel)="value"` / `(ngModelChange)="filter($event)"`, which fires the table's filterCallback on every keystroke, no Enter needed.

**Real bugs found and fixed, worth remembering the *shape* of for next time:**
1. **PrimeNG `p-menu`/`p-contextMenu` `[model]` bound to a getter silently swallows real clicks.** A getter returns a brand-new array (+ new `command` closures) on every Angular CD tick; a real click is `mousedown → CD tick → mouseup → click`, and PrimeNG rebuilds the menu's `<li>` DOM whenever `[model]` gets a new array reference — so the menu rebuilds itself mid-click and the pending click lands on a now-detached element. Invisible with a raw synthetic `element.click()` (single event, no gap), breaks with any real mousedown/mouseup sequence (including Playwright's default `.click()`). **Fix**: `computed()` if there's a real reactive dependency (tracked signals don't retrigger the array unless they actually change value), or a plain `readonly` field assigned once in the constructor if not — row-specific data can still be read live *inside* each command closure without needing the array itself rebuilt. First found on `rowContextMenuItems`, then proactively applied to the export menus too.
2. **`::ng-deep .some-class { ... }` can silently no-op depending on where PrimeNG puts the class.** `styleClass` on `p-selectButton` lands on each individual child `p-togglebutton`, not a wrapper — a descendant-combinator selector (`.export-format-select .p-togglebutton-checked`) never matched since they're the same element; needed a compound selector. Separately, `styleClass` on a plain `p-button` lands on that same-scope-as-child `<button>`, which is OUTSIDE the host component's own Angular view-encapsulation scope (it's rendered by PrimeNG's Button component's own template) — a *bare* class selector with no `::ng-deep` silently never matches for the exact same underlying reason `.p-dialog`/`.crudstone-gallery-mask` needed `::ng-deep` earlier. When a `styleClass`-driven rule "does nothing," check computed style + the actual DOM location of the class before assuming a specificity fight — it's often not being scoped there at all.
3. **CSS specificity ties are broken by *load order*, not just selector weight**, when a third-party library injects its own stylesheet at runtime after Angular's. `.export-format-select.p-togglebutton-checked` (2 classes) tied with PrimeNG's own `.p-togglebutton.p-togglebutton-checked` (also 2 classes) — PrimeNG's rule loaded later and won. Fixed by adding a tag-qualifier (`p-togglebutton.export-format-select...`) purely for extra specificity, not scoping.
4. **A "checked" toggle state can be invisible even with a correct color rule**, if the checked visual is actually an *inner* elevated pill element (`.p-togglebutton-content`, separately styled by the library) sitting on top of the *outer* element you colored — the outer element's new background paints behind, unseen, and if the label text color is also white, it's now invisible against the inner pill's still-white background. Always verify by screenshot after a "make the selected state more visible" CSS change, not just a computed-style check on the element you targeted.
5. **PrimeNG's paginator rows-per-page dropdown isn't portaled to `<body>` by default** (only the table's OWN theme CSS scopes `overflow` under `[scrollable]="true"`, which this app doesn't use) — a `.table-window`'s `overflow: hidden` (added for rounded corners) clips it. Fixed with `paginatorDropdownAppendTo="body"` on `<p-table>`.
6. **`p-table`'s non-scrollable mode has no horizontal-overflow containment at all** — a wide `tableStyle.min-width` table just blows out its container/the page on narrow viewports. `[scrollable]="true"` is the "real" PrimeNG fix but restructures the DOM (separate frozen-header scroll region); lower-risk fix used here: `overflow-x: auto` on `.p-datatable-table-container` directly.
7. **`p-table.clear()`/`.reset()` reset filters AND sort together with no way to do just one** — for separate "Clear all filters"/"Clear all sorts" buttons, replicate each half of `clear()`'s own source individually. Easy to miss: the non-lazy branch also explicitly sets `table.totalRecords = table.value.length` — the paginator's "of N entries" reads that explicit property, NOT `filteredValue.length` reactively, so skipping it leaves the entries count stale after a filter clear even though the visible rows are correct.
8. **PrimeNG `p-contextMenu` has a `breakpoint` input, default `960px`** — below that viewport width it switches into `.p-contextmenu-mobile` mode, where a NESTED submenu (e.g. this app's per-row "Export → CSV/Excel/SQL" flyout) requires a **click** to expand instead of hover. This is intentional touch-friendly PrimeNG behavior, not a bug — a user "resizing the screen and the context menu doesn't appear" was actually hovering a submenu trigger that now needs a click. Confirmed via `.p-contextmenu-mobile` class presence + testing click vs hover directly; no code change needed.
